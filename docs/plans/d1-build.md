# Plan: build variation D1 (Dashboard) into the app

The owner picked D1 from round 2 (`docs/design/variations/round-2/variants/d1.js`, artifact https://claude.ai/artifact/FrNNQtYKNHQcBxhF7JSDUK). D1 is the visual and behavioural target for the shell, Inbox, Claim and Denials. Every other screen gets D1's shell, tokens and type, with its layout tidied but not redesigned. The demo script stays at 8 steps. Work lands on `feat/d1-dashboard`, then a PR to `main`.

The prototype took its copy from a hand-written `copy.json` and derived whose-move in the browser. The app may do neither (CLAUDE.md: never render a number or fact the server didn't compute). So the build has a server half. These decisions were red-teamed (`docs/design/red-team/challenge-d1-build-2026-11-08.md`, read it) and the result is adopted below. When merged, fold this into ADR-0008 and delete the plan.

## Decisions

1. **Whose move is a server field, and it knows the viewer.** `ClaimSummary.move = {who: practice|agents|payer|nobody, holder_role, holder_user_id, label}` built in `readmodels/claims.py summarize()`. A claim with a queued or running run is `agents`. The UI says "You" when `holder_user_id`/`holder_role` match the viewer, else names the holder ("Dr. Morgan signs"). `Strip.moves[{who,count,cents}]` beside `tiles`, per-tile `by_holder` (for the Denied tally), and `inbox_claims` for the KPI line. Invariant test: moves sum exactly to open claims; tile `by_holder` sums to the tile count.
2. **Action wording comes from the action catalog,** so "what this does" is what runs. `ActionSpec.phrase(params)` gives `InboxItemOut.action_label` ("Send 3 x-rays and resubmit"); `touches: list[str]` comes from the recipe step labels (`executor.py` ~827) plus `hold_window`; `signer_note` when the required role isn't the viewer's. Reuse `phrase` for `Run.action_label` (today the lower-cased enum name, `services/inbox.py` ~77). No new headline fields: use `recommendation`/`summary`/`title`. The client `stepLabel()` in `src/lib/runEvents.ts` goes; show `RunStep.label`.
3. **What changed is computed in the approve service, not the executor.** `ApproveOut.changes` and `GroupApproveOut.changes: [{label, from, to, note?}]`, computed in one transaction in `services/inbox.py` (approve resolves the item before the run starts, a group makes several runs, and the executor has no viewer). "Denied stays 5" is a row with equal from/to. Plus `Run.claim_outcome` (the run's own claim after it ends), added to the eval `RunShape` so deterministic and live must agree.
4. **Where the baton lands** is the post-run claim `move`. For a group, read it after every run in the launch has finished.
5. **The run owns the pane (fixes R1, R2).** Build on the existing `Launch` and `?launch=` URL state with one shared `useActiveLaunch` hook (the claim page approves too). While a launch runs, Approve is disabled only for items on the same claims; J/K/Next stay live. The detail pane shows steps live, then `changes`, then Next.
6. **Styling: keep the token names, change their values** (`border-line`, `text-soft` etc. are used across every feature). Add party tokens (`practice`, `agents`, `payer`), `act` (cobalt, the only action colour), `risk`. Geist is self-hosted (npm `geist` or `@fontsource`), not Google Fonts. Scale 12/13/14/16/22/34. Shared components are restyled in place.
7. **Tests.** Keep landmarks, `data-*` and test-id selectors; visible copy may change where D1 changes it, with the spec updated in the same commit. Pipeline cells stay links. "Runs you started" stays, collapsed. `demo.spec.ts` is split into one file per screen so sessions don't collide. New tests: moves invariant; MSW `move`/`changes` parity with the API on the canonical seed; no Approve enabled for a claim under a running launch.
8. **D1's rough spots are not copied:** the long history label masked by a halo is fixed properly; the Inbox nav count uses `strip.inbox_open`.

## Phase 0 notes (`d1-contract`)

Judgment calls met while writing the schema-only change. Lean first; red-teamed below.

1. **The `{label, from, to, note?}` row.** `from` is a Python keyword. (A) `from_` with `alias="from"`, as `AdvanceAccepted` does; (B) wire names `before`/`after`; (C) `from_value`/`to_value`. **Lean B:** no alias to forget on construction (`populate_by_name` is off), reads plainly in TS, and the values are strip numbers before/after one approval. Type `int` (counts; money stays cents if a row ever needs it). Model name `StripChange`.
2. **A stable key on that row.** D1 finds the Denied row by `label === 'Denied'`, so copy edits would break the tally. (A) label only; (B) add `key: str` (a tile status, `inbox`, or `moves.<who>`). **Lean B.**
3. **`by_holder` shape.** (A) `list[HolderCount{who, holder_role, holder_user_id, count}]`, same holder fields as `ClaimMove` so the web compares with the session user one way; (B) `dict[MoveWho, int]`, which can't tell "you" from "Dr. Morgan". **Lean A.** `Strip.moves` is `list[MoveCount{who, count, cents}]`: viewer-neutral, "Yours" comes from `inbox_open`/`inbox_claims`.
4. **Required vs default.** Read-model fields in `schemas.py` are required with no default (the convention there; generated Zod then makes them non-optional in both directions, and MSW must send them). `Run.claim_outcome` is a stored entity field, so `= None` like its neighbours (old rows load). `action_label`/`signer_note` are `str | None` (None when there is no proposed action / the viewer can sign), not `""`.
5. **`MoveWho` lives in `domain/enums.py`,** because `Run.claim_outcome` (domain) needs it; `ClaimOutcome` is a value in `domain/values.py`.
6. **Stubs.** `move = {who: nobody, holder_role: null, holder_user_id: null, label: ""}`, `moves = []`, `by_holder = []`, `inbox_claims = 0`, `action_label = null`, `touches = []`, `signer_note = null`, `changes = []`, `claim_outcome = null`. Same in the API and MSW. Nothing renders them yet; phase 1 replaces every one and adds `claim_outcome` to the eval `RunShape`.
7. **Splitting `demo.spec.ts` while steps share state.** The MSW db lives in the tab's sessionStorage, so state can't cross files or browser contexts. (A) one test whose body calls per-area step functions; (B) Playwright's documented "test list" pattern: `e2e/demo.spec.ts` declares a serial describe with one page made in `beforeAll` and imports one registration function per area from `e2e/demo/*.story.ts`, each adding its own `test()`; (C) each area file replays earlier steps as setup. **Lean B:** each area reports pass/fail on its own, a failure skips the rest as before, the order lives in one 20-line file, and sessions edit only their `*.story.ts`. C doubles run time and duplicates the story. The two standalone tests become their own spec files.

**Red-team result, adopted** (`docs/design/red-team/challenge-d1-contract-2026-11-08.md`, hiring Director of Engineering persona):

- 1: `before`/`after`, int, and `note` has no default.
- 2: `key` is a closed `StripChangeKey` Literal: `inbox`, `inbox_claims`, `tile.<status>`, `move.<who>`.
- 3: `HolderCount` and `ClaimMove` both carry `mine: bool`. The server owns the one "is this mine" rule, and the web never compares holders itself. d1-api threads the viewer into `summarize()`.
- 4, 5: kept. A paused run has no `claim_outcome`; it is set at a terminal status.
- 6: stubs satisfy the invariants:
  - `moves` has four rows, with every open claim under `nobody` (matching each claim's stub `move`), and `by_status` filled for that row.
  - `by_holder` is one `nobody` row equal to the tile count.
  - `inbox_claims` and `inbox_visits` are real distinct counts.
  - `test_invariants.move_totals` and the MSW `invariants()` check all of it now.
- Fields the red team found missing, added as stubs:
  - `InboxItemOut.lands`
  - `Strip.inbox_visits`
  - `MoveCount.by_status`
  - `TimelineEntry.who`
  - `InboxGroup.action_label` / `touches`
- Not added: "paid claims still in your Inbox" (drop that D1 tooltip) and plain procedure names. d1-api decides the second and may add the field, since it owns codegen. Recommendation to the coordinator: route later contract gaps through d1-api or a coordinator contract commit, not the browser.
- 7: changed to A. `e2e/demo.spec.ts` is one test that calls per-step functions in `e2e/demo/NN-*.ts`, split by step with an owner table in `e2e/demo/README.md`, and step 10 is split into Cash and Denials. Not adopted: a `goto` plus "inherited state" assertion at the start of each step. It would change what is asserted, which phase 0 must not do. Owners may add it.

## Phase 1 (api) notes (`d1-api`)

Judgment calls met while filling the stubs. Lean first; red-teamed below.

1. **Whose move, claim by claim** (`readmodels/moves.py`, one function; `summarize(snap, claim, viewer_id)`). First match wins:
   1. closed claim → `nobody`;
   2. a queued, running or paused run on the claim → `agents` ("With the agents");
   3. an open inbox item on the claim → `practice`. Holder = the item the viewer can act on, else the top-priority item. `holder_role` = the item's `required_role`, else the tier-3 role, else `billing` (the shared queue); `holder_user_id` = its assignee. `mine` = the viewer can see *and* approve it (same rule as `visible_inbox` + `_check_authority`). Label: "Waiting on you" / "Dr. Morgan signs" (tier 3, sole role holder) / "Waiting on Dana S." / "Waiting on billing";
   4. a claim hold → by `HoldReason`: unsigned note, procedures not in note, rendering mismatch → `practice` (dentist); missing image, bad subscriber ID, other → `practice` (billing); awaiting primary EOB, reprocessing requested → `payer`;
   5. a queued (not departed) file entry → `agents` ("In the 11:15 AM Delta file");
   6. by status: `ready` → `agents`; `sent`, `accepted`, `pending`, `appealed`, `denied`, `rejected` → `payer` ("Waiting on Delta"); `partial` → `payer`; `paid` → `nobody` ("Finished").
   D1's prototype put `sent` with the agents; **lean `payer`**: the file has left, and the next event is the payer's 999/277CA. `partial` with no open item: **lean `payer`** (an underpaid line is still being adjudicated or reprocessed; the patient share is billed by posting, not a whose-move party).
2. **`lands`** is a catalog property, not a guess: `ActionSpec.lands(params, claim_status)`: queue-for-file actions (resubmit, fix and resend, send claim, corrected claim) → `agents`; payer-contact actions (reprocessing, records, appeal, rep call, status check) → `payer`; `post_era_line` → `payer` when it queues a reprocessing request, else by the claim's status; `patient_transfer` → `nobody` on a paid claim, else `payer`; `write_off` → `nobody`. Claimless items (eligibility flags, sign-offs) → `null`. Test: on the canonical seed, every approvable item's `lands` equals its run's `claim_outcome.move_to`.
3. **`action_label`** = `ActionSpec.phrase(params, payer_short, n, drafted)`, one phrase function per action in `catalog/phrases.py`, sentence case, active, naming what happens; matches `copy.json` for the canonical items where params allow ("Send x-ray and resubmit", "Send 3 x-rays and resubmit", "Send this note to Delta" for a drafted reprocessing request, "Send prompt-pay request", "Update ID and resend", "Move $38 to patient", "Hold for reprocessing", "Sign write-off and bill patient"). Eligibility flags are not catalog actions: "Note it for the front desk" (what approve does). `Run.action_label` uses the same phrase.
4. **`touches`**: each `RecipeStep` gains an optional `effect` (what it changes outside TorchRCM, counted: "x-ray uploaded to NEA"); `touches` = the effects of the steps that will run, counted across a group ("3 x-rays uploaded to NEA", "3 claims resubmitted"), then one reversibility line from `reverses_in` + the hold window ("Next Delta file, 11:15 AM", "Cannot be recalled after 11:15 AM" / "Cannot be recalled once sent" / "Can be undone until day close"). Tier 3 has no recipe, so its touches come from the amount params ("$228 written off", "$1,012 moved to patient balance"); the run records the signer's decision. Alternative rejected: touches = the step labels verbatim, which repeats the run pane and says what is done, not what changes.
5. **Recipe step labels become plain sentence case** ("Fetch the PA x-ray from imaging", "Upload to NEA", "Write the NEA# on the claim", "Queue for the 11:15 AM Delta file"), because phase 2 shows `RunStep.label` directly. Names stay (seed history and eval key on names).
6. **`signer_note`** when the viewer can't approve: from `TIER3_ROLES` + the action's tier ("Writing off money commits the practice, so only Dr. Morgan can sign this."). Null when the viewer can approve.
7. **`changes`**: `strip(viewer)` before and after, inside the approve transaction. Rows: `inbox`, `inbox_claims`, the tile of each approved claim's status (always, so "Denied stays 5" is a row with equal before/after), then every `move.<who>` row that changed. `note` only on an unchanged tile: "Stays denied until Delta replies".
8. **`claim_outcome`**: `status_from`/`move_from` read when the run first starts, with the run itself excluded and, for an approval run, its item counted as still open (so an approval reads `practice → …`); `status_to`/`move_to` at the terminal status, with the run excluded. Cancel sets it too. Added to `RunShape`.
9. **`TimelineEntry.who`**: built → `agents`; file queued → `agents`, departed → `payer`; payer acks → `payer`; a run → `agents` while active, then its `claim_outcome.move_to`, or `practice` if it opened an item; a paid remittance → `nobody` when the claim is paid; a human approve → `agents`; anything else `null` (unchanged).
10. **Plain procedure names**: add `ClaimSummary.procedures_plain` ("Crown, tooth 30 + 1 more") from a short-name column added to the CDT catalog (`world/fees.py`). No CDT dictionary in the browser.

**Red-team result, adopted** (`docs/design/red-team/challenge-d1-api-2026-11-08.md`, dental billing lead persona). The one reason that carried: name a payer only on evidence the payer owes a response, because unworked A/R must not hide behind "Waiting on Delta".

- 1, whose move, changed:
  - A paused run stays `agents` ("Agents paused"). Payer outages fail runs; they don't pause them.
  - Awaiting a primary EOB → `payer` ("Waiting on the primary payer's EOB").
  - `ready` → `agents` only while the send-claim rule is Auto, else `practice` ("Ready to send").
  - `sent` → `payer` ("Sent 10/27, no reply yet"), or `practice` ("No reply from Delta since 10/27") after 2 business days with no payer acknowledgment.
  - `rejected` → `practice` ("Rejected, not resent"). The payer never adjudicated it.
  - `denied` and `partial` → `payer` only if something left after the last remittance (a departed file entry, a filing run that succeeded, or `in_flight`). Otherwise `practice` ("Denied, nothing filed" / "Underpaid, nothing filed").
  - `label` stays viewer-neutral, as the schema says. `mine` carries the viewer.
- 2, `lands`, changed: it isn't a per-action table. Filing actions (anything queued for a payer file) → `agents`; payer requests that expect an answer (reprocessing, records, appeal) → `payer`; everything else → the whose-move rules with the item resolved. `post_era_line`'s `then` is not executed by any recipe, so it does not move the baton. Test: `lands == claim_outcome.move_to` for every approvable canonical item.
- 3, `action_label`, changed. "Post Cigna's payment, dispute $32". Tier 3 has no recipe: nothing posts a write-off, so the label is "Sign $228 write-off, $1,012 to patient" and the touches say what is left to post. "Send this note to Delta" only for a `review_draft` item.
  - **Not adopted here:** a new tier-2 `reprocessing_letter` action. It would change the catalog, the tool enums and so the cassettes. Recorded for the coordinator.
  - **Partly adopted:** `ReprocessingParams.attach` is now passed to the payer submit.
- 4, `touches`: adopted with reversibility per effect ("3 x-rays uploaded to NEA", "3 claims in the 11:15 AM Delta file", "Can be pulled from the file until 11:15 AM"; "Cannot be recalled once sent"). The file time is predicted at read time, the same way the recipe predicts it.
- 5, step labels: adopted, including "Write the NEA# and original ICN in the claim remarks". Only steps a recipe runs.
- 6, `signer_note`: adopted, built from the users who hold the approver roles.
- 7, `changes`: adopted. No `move.*` rows: at approve time they only say "agents +N", and the landing comes from the post-run `move` (decision 4). An unchanged tile gets a note: "Stays denied until Delta processes the resubmission" / "…until Delta replies".
- 8, `claim_outcome`: adopted.
- 9, `TimelineEntry.who` = the actor, always: human → `practice`; agent → `agents`; payer and clearinghouse acks and remittances → `payer`; a visit → `practice`; file entries → `agents`.
- 10: `procedures_plain` = "D2740 Crown, tooth 30 + 1 more" (code kept; billing staff work by code).
- Not adopted: counting `inbox_claims` over `move.mine`. It is defined as the claims behind the viewer's Inbox items, and #4611 is in Dana's Inbox. The KPI copy should say so.

## Phase 2 (inbox) notes (`d1-inbox`)

Judgment calls met while building D1's Inbox. Lean first; red-teamed below.

1. **The headline.** D1's h1 is hand-written ("Delta needs the PA x-ray for this crown"); the contract has no headline field (decision 2). (A) h1 = `title` ("Denial · Delta Dental · missing PA x-ray · #4821"), why = `summary`, "agent recommends" = `recommendation`; (B) h1 = `recommendation`, why = `summary`, no recommends column; (C) h1 = `summary`'s first sentence, falling back to `title`. **Lean A:** every item has a title, nothing is cut on the client, and the recommendation keeps its own column as in D1. Gap for the coordinator: a plain `headline` field.
2. **Track record.** D1 leads with "23 of 25 …" and drops the percent. (A) Show `confidence.basis`, bolding a leading "N of M", then the server's `pct` as "92%"; with `pct` null the basis is the honest no-record reason ("no base rate (n = 4)"). (B) D1 exactly (no percent). **Lean A:** the percent is a server number a reviewer has seen elsewhere; dropping it would hide the meter's source.
3. **"Can learn to run alone" vs "off the table".** No server field says whether an item's rule is learnable; `POST …:always-auto-run` answers with `422 root_cause_guard` / `tier_not_learnable`. (A) Tier 1: a quiet "Always auto-run this…" link whose server answer (proposal created, or the refusal's own message) shows inline; tiers 2 and 3: no link, `stopped_by` already says why. (B) Derive learnability on the client from tier and `root_cause`. **Lean A:** B would put a Policy decision in the browser (hard rule: the Policy layer is the only decider). Gap: a `learnable: {ok, reason}` field.
4. **The run owns the pane.** `?launch=` set → the decision pane shows the launch: a relay row per claim (baton: `agents` while the run is not terminal, then `Run.claim_outcome.move_to`), steps from `RunStep.label` live over SSE, then `launch.changes` (server; equal before/after reads "stays N", the Denied row carries the tile's `HolderTally`), then "Next: <item>" / "Stay here". Selecting another item (J/K, click, Next) drops `launch` from the URL; the run carries on and stays under "Runs you started". (Alternative: keep the run pane pinned until dismissed, rejected: it blocks J/K, which is R2.)
5. **Lock scope.** `useActiveLaunch` locks Approve for items whose `claim.id` is under a launch run that is not terminal, reading the server's run status (polled at 1.5 s when no panel streams it). - 2, `learnable`: `agents/learning.learnable()` goes through the same guard as `assert_learnable`. `POST …:always-auto-run` refuses with that function's `code` and `reason`, and `guard_learning` stays as defence. The function adds `not_enough_evidence` when n < 5. Wording per the report, except the ok line: "You can propose running this without review. Nothing changes until the proposal is accepted." The report's "The owner decides" was not used, because billing may accept proposals too. The root cause computed now reaches the read model through `Snapshot.root_cause_now`, which the API context sets. Test: over every open item, `learnable.code` equals the endpoint's answer. - 3, `Confidence`: `k: int`, `n: int` and `outcome: str` are required (`n = 0` means no history). A validator enforces `0 ≤ k ≤ n`, and `pct` is set exactly when n ≥ 5, as `round(100k/n)`. "30 d" becomes "30 days". When n is 1 to 4 the basis reads "Only 3 past cases like this, too few for a track record yet."; when n is 0 it reads "No past cases like this yet.". The client bolds `{k} of {n}` and never parses `basis`. Stored rows from before this change need `make seed`.
- 4, `409 claim_busy`: one predicate (`moves.active_runs`, the one whose-move uses for `agents`). Approve again when they finish." for a running claim, and "Agents are paused with a run open on #4821. Resume the agents or cancel that run first." for a paused one.
