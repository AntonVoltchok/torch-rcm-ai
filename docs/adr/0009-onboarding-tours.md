# ADR-0009 — Onboarding tours in the app

Status: accepted · 2026-11-09

## Context

The owner approved an interactive mock of the onboarding (`docs/design/onboarding/`, artifact https://claude.ai/artifact/3ErpLqW7EYjSrruLu4HMKi): one main tour that follows K. Owens #4821 through the whole loop, a tour per screen, every step a two-column card with the payload behind it. Settled by the owner: evaluator perspective; the main tour opens on every load and can be exited at any step; screen tours open on a screen's first visit; code panes are open by default with a remembered "Hide code"; entry points are a sidebar row with a menu, a `?` in each screen's header, and the welcome modal. The mock's twelve decisions (D1–D12) hold. This ADR records how the tours are built in the app and the calls a reviewer could have made differently (D13–D19 in DECISIONS.md, red-teamed).

## Decision

**Module.** `apps/web/src/features/tour/`: `registry.tsx` (every tour as data), `TourProvider` (mounted in `RootLayout`, state + auto-open + Try-it runner), `TourLayer` (spotlight hole, card, welcome/finish modal, keys), `TourEntry` (sidebar row + menu, header `?`), `CodePane`, `useAnchorRect`, `anchors.ts`, `screens.ts` (route → tour, built from `nav.ts`), `store.ts`, `payloads.ts`. The only new colour token is `--color-shade` (the dim overlay).

**Anchors.** Steps point at `data-tour="…"` attributes on the real elements. A missing element is said in the card ("Not on screen right now", with the step's own reason) after a grace period; the card never points at nothing.

**Numbers.** Step copy is a component that reads its numbers through the app's own hooks and query keys, so the tour and the screen share one cache. Every count or amount goes through `<Num>`; a test renders every step against MSW and fails on any digit outside a `<Num>` that is not an identifier or code, and on number words beyond a short list of spec constants.

**Code panes.** API panes read the same TanStack Query entry the screen rendered (same key and typed client, `staleTime: Infinity`, so the pane never refetches over the screen). Model-facing panes (CASE FACTS, the plan, strict tool schemas, the policy rows and decisions, the guard, the recipe, source excerpts) are text files generated by `make tour-payloads` (`apps/api/scripts/tour_payloads.py`) from a throwaway seeded DB, by symbol rather than line range; an API test fails when a committed file drifts. Each pane is tagged: live response, GET + SSE in cache, rendered on the seed, verbatim source, or hand-authored recording.

**Try it.** A Try-it presses the real control; the tour imports no mutation hook (D13). It runs under an AbortSignal that exit aborts, watches the mutations its press started (a refusal ends the wait with the server's message), and the main tour's Try-its that change the practice lead the finish to offer the owner's reset.

**Interaction.** The shell is `inert` while a tour is up; the card is a dialog with a Tab cycle; ← → Enter Esc are captured at the window before the app's shortcuts. Steps navigate with `replace`; any other navigation ends the tour. The main tour signs in as Dana past the welcome and restores the viewer on exit. Reduced motion turns off the hole's transition.

**Auto-open.** The main tour on every load (dismissal lasts one load); a screen tour on the first navigation to its screen (localStorage, per browser). `torchrcm.tour.autoopen=false` turns both off; the existing Vitest setup and `freshDemo` set it, the tour specs clear it.

## Consequences

- Copy cannot drift from the data: after the tour's own Approve the run step reads the server's `changes`, not a number typed at design time.
- Adding a screen to `nav.ts` without a tour fails the registry test; changing the agents code without regenerating payloads fails the drift test; editing `MockOnlyBanner.tsx` regenerates `mockonly.txt`.
- The tours touch screens only through `data-tour` attributes, two `data-rule`/`data-mode` attributes on the mode control, a `tour` prop on `DataTable`, and the header `?` (in `PageHeader`, and in the Denials and claim-detail headers, which have none).
- Every load of the app shows the welcome, including a refresh or a new tab (the owner confirmed this, D20); a presenter dismisses it with Esc.

## Alternatives rejected

Tour state in the URL (D15); calling mutation hooks from the tour (D13); detecting `navigator.webdriver` to stay out of tests (D16); letting clicks through to the spotlighted element (D17); per-persona memory (D14). Reasons and the red team's verdicts are in DECISIONS.md and `docs/design/red-team/challenge-onboarding-tours-impl-2026-11-09.md`; the implementation red team's findings and fixes are in `docs/design/onboarding/red-team.md`.
